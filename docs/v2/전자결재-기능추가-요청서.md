# CRM 전자결재 기능 추가 요청서

작성일: 2026-09-17 · 상태: 개발 검토용 초안 · 우선순위: 협의 · 요청/검토 담당자: 추후 지정

## 1. 요청 요약

기존 CRM 안에서 업무 요청서를 작성하고, 지정된 담당자의 순차 결재를 받아 처리 결과와 이력을 확인할 수 있는 전자결재 기능을 추가하고자 합니다.

**도입 원칙은 ‘기존 업무 흐름을 유지하면서 독립적인 결재 기능을 추가’하는 것입니다.** 초기에는 결재 문서에서 고객·프로젝트·매출 회차를 선택해 참조할 수 있도록 하고, 결재 결과에 따른 원본 데이터 수정이나 기존 업무의 필수 결재 전환은 별도 범위로 검토합니다.

개발팀은 아래 사용자 요구와 수용 기준을 충족하는 범위에서 기존 구조에 적합한 구현 방식을 제안해 주세요. 본 문서의 경로·테이블명·화면 구성은 설계 제안이며 확정된 구현 지시가 아닙니다.

## 2. 검토 기준과 기존 구현 확인

저장소에는 의료 CRM 구버전(`m-crm-project`, `mcrm-backend`)과 통합 마케팅·고객 관리 v2(`mcrm-v2`, `mcrm-v2-backend`)가 공존합니다. 최근 v2 문서와 실제 코드를 기준으로 본 요청서를 작성했습니다. 운영 서버나 운영 DB를 직접 검증한 문서는 아니므로 착수 시 실제 배포 버전과 일치하는지 확인해야 합니다.

| 영역 | 로컬 코드에서 확인한 내용 | 추가 개발 시 적용 원칙 |
|---|---|---|
| 사용자·인증 | v2의 기존 사용자 계정, Sanctum 인증, 활성 계정 속성 | 별도 로그인·계정 체계 없이 기존 인증 사용 |
| 역할 | 대표·이사·팀장·담당자·관리자 역할 | 기존 역할명·권한을 일괄 변경하지 않고 결재 기능 권한 추가 |
| 고객·매출 | 유입 고객, 기존 고객, 프로젝트, 매출 회차, 정기 관리 | 결재 문서에서 기존 항목을 참조하고 원본은 기존 기능에서 관리 |
| 매출 확정 | `Contract`의 완료 상태와 금액, 수금일 기준 공용 집계 | 결재 완료를 매출 완료나 입금 확인으로 취급하지 않음 |
| 지출결의서 | `expense_requested`가 기존 비용 인정 조건에 사용됨 | 신규 결재 상태로 대체하거나 자동 변경하지 않음 |
| 이력 | 고객 변경 이력과 계약 변경 이력 분리 | 결재 이력을 추가하되 고객 단계·KPI 이력에 섞지 않음 |
| 알림 | v2 알림은 수집 실패·입력 지연 등 현재 조치 상태를 조회하는 방식 | 영구 보관·읽음 처리 알림이 이미 존재한다고 가정하지 않음 |
| 메뉴 | 공통 그룹 탭을 사이드바와 공유 | 실제 사용 중인 공통 메뉴 정의에 연결 |
| 배포 | 최신 v2 문서는 VPS/Docker 운영을 기술 | 구버전 Cafe24 배포 절차를 그대로 적용하지 않음 |

구버전의 `clinic_id`, 사용자 기본키 `user_id`, 알림 테이블을 v2에 그대로 이식하지 않습니다. v2의 조직·부서 단위 접근 구조는 별도 확인이 필요하며, 초기 문서 접근은 참여자 중심으로 설계합니다.

## 3. 목적과 사용 예시

- 메신저·구두로 처리하던 요청과 승인 결과를 CRM에서 확인할 수 있게 합니다.
- 어떤 내용이 누구에게 요청되었고, 누가 언제 승인·반려했는지 남깁니다.
- 고객·프로젝트 관련 문서를 해당 업무와 함께 찾을 수 있게 합니다.
- 문서 양식과 결재 순서를 확장할 수 있도록 하되, 초기 기능은 단순하게 유지합니다.

초기 후보 양식은 **일반 업무 요청서, 지출결의서, 구매 요청서**입니다. 예산 승인·할인·환불·계약조건 변경은 향후 양식 확장 후보이며 실제 금액 변경, 지급, 광고 플랫폼 예산 조정까지 포함하지 않습니다.

예: 담당자가 프로젝트를 참조해 지출결의서를 작성 → 팀장 → 대표 순으로 결재 → 최종 승인된 문서를 기존 지출 처리 업무의 근거로 활용. 승인만으로 비용·매출·수금일·기존 지출결의서 체크값이 변경되지는 않습니다.

## 4. 개발 범위

| 구분 | 포함 기능 |
|---|---|
| 1차 필수 | 문서 작성·임시저장·상신, 지정 사용자 순차 결재, 승인·반려·회수, 참조자, 문서함·검색, 첨부파일, 결재 이력, 인앱 대기 표시, 선택적 CRM 참조 |
| 1차 기본 설정 | 사용할 양식, 양식별 필수 항목, 기본 결재선, 결재 가능 사용자, 기능 활성화 대상 |
| 후속 선택 | 금액별 결재선, 병렬 결재·합의, 대결·전결, 부재자 대체, 완료 문서 출력/PDF, 이메일·메신저 알림, 결재 처리 통계 |
| 별도 연동 개발 | 승인 결과의 CRM 자동 반영, 특정 업무의 필수 결재, 회계·지급 시스템 연동, 광고 플랫폼 변경 |
| 이번 범위 제외 | 인사·급여·휴가 시스템 전체, 조직도 구축, 외부 전자서명·계약 서비스, 기존 데이터 일괄 전환 |

완전한 드래그형 양식 편집기나 범용 워크플로 엔진은 1차 필수 요건이 아닙니다. 기본 양식을 설정 기반으로 추가·수정할 수 있는 수준으로 시작해도 됩니다.

## 5. 상세 기능 요구사항

| ID | 기능 | 요청 내용 |
|---|---|---|
| EA-01 | 문서 작성 | 양식, 제목, 요청 내용, 기안자를 관리. 금액·희망 처리일·CRM 참조·첨부는 양식별 필요 여부 설정. 기안자는 서버 인증 정보로 확정 |
| EA-02 | 임시저장 | 본인 임시 문서 저장·수정·삭제. 필수 항목 검증은 상신 시 적용. 다른 사용자는 임시 문서 접근 불가 |
| EA-03 | 결재선 | 활성 사용자 중 결재 권한 보유자를 순서대로 선택. 기본 결재선 제공, 사용자 수정 허용 여부는 양식별 설정. 중복 결재자·기안자 본인 지정은 기본 차단 |
| EA-04 | 상신 | 필수값·결재선·참조 권한을 서버에서 검증. 상신 시 문서번호 발급, 내용·양식 버전·결재선·첨부 목록 확정 |
| EA-05 | 순차 결재 | 현재 차례의 결재자만 승인·반려 가능. 승인 시 다음 단계 이동, 마지막 승인 시 최종 완료. 반려 사유 필수 |
| EA-06 | 회수·재상신 | 첫 승인 전 기안자 회수 허용. 반려·회수 문서는 새 차수로 수정·재상신하고 이전 내용·결재 이력 유지. 승인 이후 회수는 1차 제외 |
| EA-07 | 문서함 | 내가 기안한 문서, 내가 결재할 문서, 내가 처리한 문서, 참조 문서 제공. 상태·양식·기안일·제목·문서번호로 검색 |
| EA-08 | 상세 화면 | 본문, 결재선과 단계별 처리 시각·의견, 첨부, CRM 참조, 재상신 차수와 이력을 한 화면에서 확인 |
| EA-09 | 참조자 | 상신 시 확정된 참조자는 문서 열람 가능, 결재 권한 없음. 상신 후 참조자 추가·변경은 1차 제외 |
| EA-10 | 첨부파일 | 허용 확장자·용량·개수 설정. 비공개 저장, 조회·다운로드 시 문서 권한 검사. 상신된 파일은 교체 불가, 새 차수에서 변경 |
| EA-11 | 알림·대기 표시 | 결재할 문서 수와 바로가기 제공. 기안자는 승인·반려 결과를 문서함에서 확인. 상신·결과 이벤트는 재조회해도 유지되는 결재 기록으로 보관 |
| EA-12 | 설정 | 권한 있는 운영 담당자가 양식·기본 결재선·사용 대상을 관리. 설정 변경은 새 문서/새 상신 차수부터 적용 |

금액은 문서의 요청 금액이며 CRM의 매출액·비용과 별도입니다. ‘결재’와 ‘결제/지급’을 화면 문구에서 구분합니다. 승인 후에도 실제 처리 여부는 기존 업무 화면에서 확인하도록 안내합니다.

## 6. 상태와 예외 처리

| 현재 상태 | 동작·조건 | 결과 |
|---|---|---|
| 임시저장 | 기안자가 상신 | 결재 진행 중, 첫 결재자에게 배정 |
| 결재 진행 중 | 현재 결재자 승인, 다음 단계 있음 | 결재 진행 중, 다음 결재자에게 배정 |
| 결재 진행 중 | 마지막 결재자 승인 | 승인 완료 |
| 결재 진행 중 | 현재 결재자 반려 | 반려, 이후 단계 진행 중지 |
| 결재 진행 중 | 기안자 회수, 아직 승인 없음 | 회수 |
| 반려·회수 | 기안자가 수정본 작성 | 새 차수의 임시저장 생성, 이전 차수 보존 |
| 승인 완료 | 내용 변경 필요 | 기존 문서 유지, 원문을 참조한 새 문서 작성 |

- 문서 상태와 개별 결재 단계 상태를 분리합니다. 문서가 진행 중이어도 다음 차례 결재자는 아직 처리할 수 없습니다.
- 상신 후 본문·금액·첨부·결재선 직접 수정은 차단합니다. 이전 승인과 다른 내용이 한 문서에 섞이지 않아야 합니다.
- 결재자 퇴사·비활성화 시 자동 승인하거나 단계를 건너뛰지 않습니다. 진행 차단 사유를 표시하고, 1차에는 권한 있는 운영 담당자의 사유 있는 ‘진행 중단’ 기록 후 새 문서를 작성하는 방식으로 복구합니다. 운영 중단은 결재 반려와 구분하며 원문·기처리 이력을 보존합니다.
- 승인·반려·회수가 동시에 요청되거나 버튼을 반복 클릭해도 하나의 유효한 상태 전이만 성공해야 합니다. 만료된 화면에는 새로고침 안내를 제공합니다.
- CRM 원본이 변경·삭제되어도 상신 당시의 최소 참조 정보와 결재 이력은 유지합니다. 현재 원본과 다른 경우 변경 또는 삭제 사실을 표시합니다.
- 첨부 업로드나 내용 저장이 실패하면 상신 성공으로 표시하지 않습니다. 알림 전달 실패는 승인 결과를 되돌리지 않고 별도 재시도 대상으로 남깁니다.

## 7. 권한과 정보 공개

기존 CRM 역할을 유지하면서 ‘기안 가능’, ‘결재 가능’, ‘결재 설정 관리’, ‘예외 문서 조회/진행 중단’ 권한을 추가하는 방식을 제안합니다. 기존 관리자나 상위 직책이라는 이유만으로 타인의 결재를 대신 처리할 수 없도록 합니다.

| 구분 | 기본 허용 범위 |
|---|---|
| 기안자 | 본인 임시 문서 편집, 상신 문서·결과 조회, 조건에 맞는 회수 |
| 결재자 | 배정된 상신 문서 조회, 본인 차례에 승인·반려 |
| 참조자 | 지정된 상신 문서 조회 |
| 설정 관리자 | 양식·기본 결재선·기능 권한 관리. 전체 문서 조회·대리 결재 자동 부여 없음 |
| 예외 운영 권한자 | 명시적으로 허용된 문서 범위 조회·진행 중단. 사유와 실행 이력 필수 |

- 목록·문서 수·검색·상세·첨부 다운로드까지 같은 접근 범위를 적용합니다. 화면 버튼 숨김만으로 권한을 구현하지 않습니다.
- 원본 CRM의 열람 권한과 결재 문서 열람 권한을 각각 확인합니다. 결재자로 지정되었다고 고객 상세나 매출 편집 권한이 생기지 않습니다.
- 문서에 복사하는 CRM 정보는 최소 항목으로 제한하고, 연락처 등 민감정보를 자동 복제하지 않습니다. 문서 참여자에게 공유되는 내용은 상신 전 확인할 수 있게 합니다.
- 계정 비활성화·권한 회수는 이후 요청부터 적용합니다. 이미 남긴 결재 기록은 보존합니다.
- 보관기간·첨부 파기·열람 범위는 운영 정책 확정 후 적용합니다. 기술적으로 무기한 보관을 고정하지 않습니다.

## 8. 기존 기능과 충돌 방지 원칙

| 충돌 가능 영역 | 1차 적용 원칙 | 추후 연동 조건 |
|---|---|---|
| 기존 ‘지출결의서 작성·전달’ | `expense_requested`의 의미·체크 동작·집계 유지. 전자결재 상태는 별도 표시 | 승인과 기존 체크를 연결할 시점, 기존 건 처리 방식, 비용 인식 영향 합의 |
| 매출·수금·비용 | 승인만으로 `status`, `paid_at`, `amount`, `cost`, `invoiced` 변경 금지 | 별도 실행 권한·업무 검증을 거쳐 기존 갱신 로직 사용 |
| 매출 등록 경로 | 결재 문서를 별도 매출 원장으로 사용하지 않음 | 기존 매출 입력의 공통 서비스로만 반영 |
| 정기·분납 프로젝트 | 프로젝트 전체와 특정 회차를 구분해 참조. 승인으로 다음 회차 자동 생성·변경 금지 | 적용 회차·적용월을 명확히 지정하고 기존 정기 생성 규칙 유지 |
| 고객 전환·KPI | 결재 문서 생성·승인이 고객 단계나 기존 고객 전환을 발생시키지 않음 | 필요한 업무 이벤트를 별도 정의 |
| 광고 성과·예산 | 예산 요청 문서의 승인 기록만 관리 | 광고 플랫폼 쓰기 연동은 별도 요청 |
| 기존 보고서·지표 | 결재 건수·요청 금액을 매출·ROAS·수익률 집계에 포함하지 않음 | 결재 통계는 별도 지표로 제공 |
| 알림 | 결재 대기와 기존 수집 실패·입력 지연을 구분 | 읽음·영구 알림 도입은 별도 저장 구조와 범위 합의 |
| 감사 이력 | 결재 전용 이력 저장, 기존 고객 단계 변경 로그에 기록하지 않음 | 원본을 실제 변경할 때만 해당 원본의 이력 규칙 적용 |
| 기능 비활성화 | 결재 기능을 꺼도 기존 CRM 업무 가능 | 후속 필수 결재 연동 도입 시 중단 정책 별도 재설계 |

기존 문서·고객·매출 데이터의 일괄 결재 문서 생성이나 과거 데이터에 대한 결재 의무 소급 적용은 하지 않습니다.

## 9. 화면 구성 제안

- **전자결재 메뉴:** 내 결재 대기 / 기안 문서 / 처리 문서 / 참조 문서. 임시저장은 기안 문서 안에서 구분합니다.
- **문서 작성:** 양식 선택 → 본문·CRM 참조·첨부 입력 → 결재선·참조자 확인 → 임시저장 또는 상신.
- **문서 상세:** 상태와 현재 처리자 → 본문·참조·첨부 → 결재선·이력 → 사용자별 가능한 동작.
- **설정:** 결재 양식, 기본 결재선, 기능 권한. 기존 사용자 관리와 중복 계정 관리 화면을 만들지 않습니다.
- **선택적 진입점:** 고객·매출 상세에서 ‘관련 결재 문서 보기/작성’. 원본 화면 수정 부담이 크면 1차는 전자결재 화면의 참조 선택만 제공해도 됩니다.

기존 디자인과 공통 컴포넌트를 사용하고 모바일에서도 조회·승인·반려가 가능하도록 합니다. 전자결재 메뉴의 위치는 현재 메뉴 체계에 맞춰 조정할 수 있습니다.

## 10. 개발팀 검토용 설계 제안

### 데이터와 API

신규 모듈 중심으로 구성하고 기존 핵심 테이블의 필수 컬럼 추가·상태 enum 변경을 최소화합니다.

| 논리 데이터 | 역할 |
|---|---|
| 결재 문서 | 문서번호, 기안자, 상태, 현재 차수, 현재 단계 |
| 문서 차수 | 상신 당시 본문·금액·양식 버전·결재선·참조자 스냅샷 |
| 결재 단계 | 순서, 지정 사용자, 처리 상태·의견·시각 |
| 결재 이벤트 | 상신·승인·반려·회수·중단·설정 변경의 추가 기록 전용 이력 |
| CRM 참조 | 허용된 원본 유형과 식별자, 최소 참조 스냅샷 |
| 첨부 | 비공개 파일 식별자, 크기·종류, 업로더, 연결된 차수 |
| 양식·기본 결재선 | 양식 버전, 필수 항목, 기본 처리자, 사용 여부 |

제안 API 영역은 `/api/approvals`와 `/api/approval-templates`, 화면은 `/approvals`입니다. 상신·승인·반려·회수는 명시적 동작으로 분리하고, 기존 고객·매출 API의 요청·응답 계약을 유지합니다. 확정 명칭은 개발팀 설계에 따릅니다.

### 일관성과 운영

- 문서 상태·결재 단계·이력을 하나의 트랜잭션으로 처리하고, 잠금 또는 버전 검사와 재요청 중복 방지를 적용합니다.
- 알림을 비동기로 구현한다면 승인 커밋 이후 전달하되 재시도 가능한 이벤트를 남깁니다. 알림 장애가 기존 광고 수집·보고서 작업을 막지 않도록 합니다.
- 결재 이력에는 처리자와 처리 당시 역할·시각·사유를 남깁니다. 일반 앱 경로에서 이력 수정·삭제를 허용하지 않습니다.
- 참조 유형은 서버 허용 목록으로 제한하고 임의 테이블 접근을 허용하지 않습니다. 원본 삭제가 결재 이력 연쇄 삭제로 이어지지 않도록 합니다.
- 결재자 선택 데이터는 기존 사용자 소스를 활용하되 활성 여부와 결재 권한을 서버에서 필터링합니다. 별도 수기 사용자 목록을 유지하지 않습니다.
- 화면과 API 양쪽에 기능 활성화 설정을 적용합니다. 신규 기능 장애가 기존 CRM API의 성공 여부에 영향을 주지 않도록 합니다.

후속 자동 반영을 도입할 경우 ‘승인 완료’와 ‘원본 반영 대기/완료/실패’를 분리해야 합니다. 승인 당시 원본과 현재 값 비교, 중복 실행 방지, 기존 일괄 변경·정기 갱신 경로와의 일관성, 영향 월 집계 재계산까지 별도 설계합니다.

## 11. 검수·수용 기준

| ID | 검수 시나리오 | 기대 결과 |

핵심 권한·상태 전이·동시 처리에는 자동 테스트를 적용하고, 기존 업무와 지표는 동일한 검증 데이터로 회귀 확인합니다. 화면 검수는 실제 역할별 계정과 모바일 크기에서 수행합니다.

## 12. 도입·전환·복구 계획

| 단계 | 할 일 | 담당 역할 | 완료 기준 |
|---|---|---|---|
| 범위 확정 | 시범 양식·결재선·권한·보관 정책 합의, 실제 운영 버전 확인 | 업무 담당자 + 개발 책임자 | 1차 범위와 제외 범위 확정 |
| 설계·견적 | 기존 구조 재사용 범위, 추가 테이블, 화면/API, 영향·공수 제시 | 개발팀 | 검수 항목별 구현 방안 제시 |
| 개발·검증 | 기능 플래그 비활성 기본값으로 개발, 백업·복구 확인 | 개발팀 | 수용 기준 통과 |
| 시범 운영 | 소수 사용자와 1~2개 양식으로 사용 | 업무 담당자 + 운영 담당자 | 권한·결재선·반려·회수 흐름 확인 |
| 확대 적용 | 사용 대상과 양식 확대 | 운영 담당자 | 장애·미처리 문서 점검 후 확대 |

일정과 비용은 범위·첨부 저장 방식·현행 권한 구현을 확인한 뒤 개발팀이 제안합니다. 견적은 필수 범위와 후속 선택 기능을 구분해 주세요.

시범 운영 전 사용자에게 기존 업무 처리와 결재 승인의 차이, 작성·반려·회수 방법을 안내합니다. 운영 문의 담당자를 지정하고, 시범 종료 시 처리 시간·반려 사유·중단 건수·사용 불편을 검토합니다.

복구 기준은 타인 문서 노출, 기존 매출 지표 변동, 결재 상태·이력 불일치 또는 기존 CRM 장애입니다. 문제 발생 시 신규 상신·결재 쓰기를 중지하고 신규 메뉴/API를 비활성화합니다. 확인된 안전한 버전으로 되돌리되 결재 테이블·첨부·이력을 삭제하지 않습니다. 읽기 안전성이 확인된 경우에만 조회를 유지합니다. 기존 CRM 정상 동작과 지표 복구를 검증하고, 원인 수정 및 진행 문서 정합성 확인 후 재개합니다.

## 13. 착수 전 결정할 항목과 제안 기본값

아래 항목은 개발 요청을 전달하기 위한 미확정 정책이며, 본 초안 작성 자체를 지연시키는 조건은 아닙니다.

| 결정 항목 | 제안 기본값 |
|---|---|
| 대상 버전 | 현재 v2. 실제 운영 배포와 일치 여부 확인 |
| 시범 양식 | 일반 업무 요청서 + 지출결의서 |
| 결재 방식 | 지정 사용자 순차 결재, 병렬·대결·전결 제외 |
| 자기 결재 | 기본 불가. 최종 직책자의 기안 경로는 시범 시작 전 지정 |
| 문서 공개 | 기안자·지정 결재자·참조자만, 예외 조회는 별도 권한 |
| 조직 단위 | 기존 계정 활용, 부서·지점 조직도 신설 제외 |
| 회수 | 첫 승인 전만 허용 |
| CRM 연동 | 선택 참조만, 승인 결과 자동 반영 없음 |
| 기존 업무 필수 결재 | 1차 미적용 |
| 알림 | 인앱 결재 대기 표시와 결과 기록, 외부 발송 제외 |
| 첨부 제한·보관기간 | 파일 형식·용량·개수·기간·파기 담당자 합의 후 운영 활성화 |

개발팀 회신에는 ① 구현 가능 범위 ② 기존 코드 영향 ③ 추가 개발 필요 구조 ④ 필수/선택 기능별 공수 ⑤ 검증·배포·복구 방안 ⑥ 정책상 추가 결정 사항을 포함해 주세요.
